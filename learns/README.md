# OpenCoWork 学习区

这里不是第二套规格库，而是小陌理解 OpenCoWork、训练 .NET 架构能力的学习记录。

## 学习目标

完成学习后，应当能够：

1. 用自己的话解释产品目标、业务闭环和关键架构取舍；
2. 从一个用户动作追到协议、Session、Agent、Tool 和持久化代码；
3. 判断一个改动会影响哪些契约、状态、测试和发布证据；
4. 在不依赖现成答案的情况下完成一个小型 Slice 的设计与实现。

不要求背类名、背目录或一次读完所有规格。能解释、能定位、能验证，才算真的会。

## 四条并行学习主线

每一课都同时从四个角度学习，不能只看功能：

| 主线 | 核心问题 |
| --- | --- |
| 业务与领域 | 系统解决什么问题，哪些状态和规则不能破坏？ |
| 架构与抽象 | 职责为什么属于这一层，依赖方向和生命周期如何确定？ |
| .NET 实现技法 | 设计如何借助语言、BCL、Hosting、DI、异步和代码生成落地？ |
| 验证与演进 | 为什么相信它正确，失败后如何恢复，未来在哪里扩展？ |

设计模式只是描述设计形状的词汇，不是课程目标。学习时先还原问题、约束和取舍，再判断它接近 Adapter、Strategy、Pipeline、State Machine、Outbox 等哪种模式，避免“看见接口就喊设计模式”。

全仓设计机制统一登记在 [00-架构设计总索引.md](00-架构设计总索引.md)。索引负责防遗漏；每一课负责把其中一组机制讲到能够复刻。

首个跨主题深度样例见 [专题-状态迁移与API版本演进.md](专题-状态迁移与API版本演进.md)。

## 资料优先级

发生冲突时，按以下顺序判断：

1. 当前代码与可运行测试；
2. 已确认的 `docs/superpowers/specs/`；
3. 交付证据 `docs/superpowers/archives/` 与里程碑台账；
4. 本目录的学习总结。

根目录的 DotCraft 规范是本机实现证据基线，不是 OpenCoWork 的产品契约，也不是入门教材。

## 学习方法

每一课只跑一个闭环：

```text
先看用户问题
→ 画最小流程
→ 找 3～5 个关键代码锚点
→ 用测试验证理解
→ 小陌复述
→ 哪吒纠偏并更新学习总结
```

判断学会的标准不是“看懂了”，而是能够回答：

- 这个设计解决什么问题？
- 为什么职责属于这里？
- 状态的权威来源在哪里？
- 失败、取消、重启时会怎样？
- 改坏后哪条测试最先报警？

## 如何开始

先打开 [01-项目全景与业务闭环.md](01-项目全景与业务闭环.md)，建立系统地图；再读 [02-Runtime架构角色与生命周期.md](02-Runtime架构角色与生命周期.md)，建立判断 Runtime 角色、所有权和生命周期的框架。答案不需要标准，暴露理解偏差才有学习价值。

以后可以直接对哪吒说：

- `开始第 1 课`
- `我来复述 Session Core，你纠正我`
- `带我追一次 turn/start 的代码`
- `把今天学到的内容总结进 learns`

每次学习结束，由哪吒更新对应课件中的总结、误区、代码锚点和掌握状态。
