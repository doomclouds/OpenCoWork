# 第 3 课：契约、程序集与抽象层

## 这一课解决什么问题

看到一个需求时，怎样判断类型应该放在 `Abstractions`、`Core`、`Protocol`、业务模块还是 `App`？什么时候值得建立接口和独立程序集，什么时候只是在给项目增加搬运成本？

这一课不追求画一张漂亮的“洋葱图”，而是学会让依赖方向服务于业务不变量、变化频率和运行时装配。

## 先说结论

依赖方向不是“上层调用下层”这么简单。更可靠的判断是：

```text
容易变化的机制
→ 依赖较稳定的业务语义和契约

最终由 Composition Root
→ 选择具体实现并把双方装起来
```

OpenCoWork 的典型链路是：

```text
Protocol ──依赖──► ISessionService（Abstractions）
                             ▲
                             │ 实现
                    SessionService（Core）
                             ▲
                             │ 组合
                         App / Module
```

调用方向可以从 Protocol 指向 Session Service，但编译期依赖不需要从 Protocol 指向 Core。这里用到的是 Dependency Inversion：高层业务规则和外围机制通过稳定契约相遇，而不是彼此直接绑死。

## 先区分四种经常混淆的边界

| 边界 | 它真正控制什么 | 它不能自动保证什么 |
| --- | --- | --- |
| 文件夹 | 代码导航和局部组织 | 不能阻止跨目录引用 |
| Namespace | 类型命名和逻辑归类 | 不是部署或访问隔离边界 |
| Assembly / Project | 编译引用、可见性、依赖闭包和发布产物 | 不自动提供进程隔离 |
| Runtime Module | 启动顺序、能力组合、生命周期和故障状态 | 不一定与程序集一一对应 |

OpenCoWork 里的 `SessionModule`、`CliModule` 都在 `OpenCoWork.App` 中，而 `AutomationsModule`、`TeamsModule` 分别位于独立程序集。所以“一个模块一个项目”不是硬规则；程序集解决编译依赖，Module 解决运行时组合，它们只是有时重合。

## 七个生产项目的真实依赖图

先只看普通运行时 `ProjectReference`：

```text
OpenCoWork.Core ─────────────► OpenCoWork.Abstractions
OpenCoWork.Protocol ─────────► OpenCoWork.Abstractions
OpenCoWork.Automations ──────► OpenCoWork.Abstractions
OpenCoWork.Automations ──────► OpenCoWork.Protocol
OpenCoWork.Teams ────────────► OpenCoWork.Abstractions
OpenCoWork.Teams ────────────► OpenCoWork.Protocol

OpenCoWork.App ──────────────► Core
             ├───────────────► Protocol
             ├───────────────► Automations
             └───────────────► Teams
```

`OpenCoWork.Abstractions` 没有指向其他 OpenCoWork 生产项目的引用。`OpenCoWork.Protocol` 也没有引用 `OpenCoWork.Core`、`Teams` 或 `Automations`。`App` 位于组合端，所以它知道所有需要装配的具体项目并不是污染，反而是 Composition Root 的职责。

还有一组不能混进上图的编译期依赖：

```text
Core / Protocol / Automations / Teams / App
                  │
                  └── Analyzer ──► OpenCoWork.Generators
```

这些 `ProjectReference` 带有：

```xml
OutputItemType="Analyzer"
ReferenceOutputAssembly="false"
```

它表示编译器运行 Generator，但生成器程序集不会成为应用运行时依赖。只有 `OpenCoWork.App` 打开 `OpenCoWorkGenerateCatalog=true`，因为最终 Catalog 应在拥有完整依赖闭包的组合根生成。

## 每个项目为什么存在

| 项目 | 拥有什么 | 不应拥有什么 |
| --- | --- | --- |
| `OpenCoWork.Abstractions` | 跨程序集 DTO、枚举、错误码、Attribute、Service Port、Module Contract | SQLite 实现、Provider SDK、协议 Handler、CLI 组装 |
| `OpenCoWork.Core` | Workspace、Session、Agent、Tool、State 等核心实现和 Hosting 基础 | JSON-RPC 输入细节、Automation/Cron 专属规则 |
| `OpenCoWork.Protocol` | Wire、JSON-RPC、ACP 的解析、版本门控、DTO 映射和错误翻译 | Session 权威状态机、SQLite 直写、具体 Core 类型 |
| `OpenCoWork.Automations` | Automation Definition、调度、Lease、Dispatcher、恢复和模块生命周期 | 复制 Thread/Turn 状态机 |
| `OpenCoWork.Teams` | Mission、Task DAG、Mailbox、Artifact、Worktree 与多 Agent 编排 | 复制 Session 或 Tool 安全管线 |
| `OpenCoWork.Generators` | 编译期声明收集、Catalog 生成和架构诊断 | 运行时业务状态 |
| `OpenCoWork.App` | 命令入口、主宿主选择、模块声明、DI 与最终组合 | 把所有业务规则重新包办一遍 |

项目数量不是架构质量指标。这里拆成七个项目，是因为这些部分具有不同的依赖方向、变化原因或编译/运行阶段；不是因为“项目越多越专业”。

## Abstractions 到底是什么

`Abstractions` 不是“所有接口的垃圾桶”，也不是一个名叫 Common 的杂物间。一个类型适合进入这里，通常是因为：

1. 两个或更多程序集需要围绕它协作；
2. 它表达稳定业务语义，而不是某个实现步骤；
3. 消费方不应知道提供方的具体类型；
4. 改动它意味着跨程序集契约变化，值得被认真审查。

它可以包含的不只是接口：

- `ThreadSnapshot`、`TurnSnapshot` 等跨边界 DTO；
- `ThreadStatus`、稳定错误码和结果类型；
- `ISessionService`、`ICapabilityService` 等应用 Port；
- `IOpenCoWorkModule` 与模块描述；
- `OpenCoWorkModuleAttribute`、`OpenCoWorkWireMethodAttribute` 等声明语言；
- 模块向共享基础设施贡献行为所需的窄契约。

反过来，如果一个接口只有一个调用者和一个实现，而且没有隔离变化或测试替换价值，就不该为了“面向接口编程”机械搬进 `Abstractions`。接口是工具，不是架构护身符。

## 一条真实调用链怎样跨越这些层

以 Wire 的 `turn/start` 为例：

1. `OpenCoWorkJsonRpcConnection` 位于 Protocol，接收并校验外部 JSON-RPC 请求；
2. 它只持有 `ISessionService` 等 Abstractions 契约；
3. `SessionService` 位于 Core，实现 sequence、幂等、状态机、Journal、投影和事件发布；
4. App 的 Composition Root 与 Session Module 注册 Core 实现并建立 DI 关系；
5. 运行时调用穿过接口，编译期依赖仍保持 `Protocol -> Abstractions <- Core`。

这里要区分：

```text
运行时调用方向：Protocol → SessionService
编译期依赖方向：Protocol → Abstractions ← Core
```

很多人把这两根箭头画成一根，于是误以为“调用了 Core，就必须引用 Core”。Dependency Inversion 解决的正是这个耦合。

## 为什么 Protocol 不能直接依赖 Core

如果 `OpenCoWork.Protocol` 直接引用 `OpenCoWork.Core` 并操作 `SessionService`、`StateRuntime` 或 SQLite：

- 协议适配器会知道内部存储和状态机细节；
- Wire、ACP 等入口可能分别绕过不同的不变量；
- Core 的内部重构会无谓破坏外部协议；
- Protocol 测试很难只围绕稳定契约构造替身；
- 未来更换宿主或提供进程外实现时，协议层无法复用；
- 最终会形成 `Protocol -> Core -> 某个外围项目 -> Protocol` 的循环。

因此 Protocol 的职责止于“翻译并调用 Port”。它可以拒绝非法协议输入、执行版本门控和映射稳定错误，但不能成为 Session 状态的第二权威。

## Core 为什么也不能反过来依赖 Protocol

核心业务不应知道 JSON-RPC 方法名、Wire 版本或终端传输细节。Core 应表达 Thread、Turn、Tool、State 等产品语义；Protocol 再把这些语义映射成外部格式。

如果 Core 开始返回 `JsonRpcResponse` 或读取 Wire DTO，换一个入口就得修改核心。正确做法是 Core 返回稳定的应用结果，Protocol 负责把结果翻译成对应协议响应。

这就是 Ports and Adapters 的基本形状：

```text
外部入口 Adapter
      │
      ▼
稳定 Port
      │
      ▼
核心用例与状态机
```

## App 为什么可以知道所有具体项目

Composition Root 是有意设置的“具体知识汇合点”。`OpenCoWorkCompositionRoot.Build` 会：

1. 从生成的 `RuntimeCatalog.Modules` 建立 `ModuleRegistry`；
2. 选择 Primary Host；
3. 创建 Generic Host；
4. 注册配置、Workspace、Core Runtime 和模块；
5. 让 `ModuleLifecycleCoordinator` 统一启动和停止。

如果为了让 App 看起来“纯净”，再给每个具体实现套一层工厂、反射扫描或 Service Locator，只是把真实依赖藏起来。组合根的价值就是把不可避免的具体选择集中、显式并可审计。

## Assembly 边界与 Module 边界怎样配合

程序集引用决定“代码能不能看见另一个项目的类型”；Module Dependency 决定“运行时必须先启动谁”。例如：

```csharp
[OpenCoWorkModule("automations", Dependencies = ["session"])]
```

它表达 Automation 运行前需要 Session 能力就绪，但 `OpenCoWork.Automations` 不需要因此引用 `OpenCoWork.Core`。它通过 Abstractions 中的 `ISessionService` 协作，由 App 在运行时提供实现。

所以两类关系不能互相替代：

- ProjectReference 管编译期可见性；
- Module Dependencies 管运行时启动拓扑；
- DI 管契约与具体实例的绑定；
- Source Generator 管分散声明的编译期汇总。

## 架构测试为什么不是多余的

只在文档里写“Protocol 不得引用 Core”守不住边界。一次顺手的 IDE 添加引用就能让规则失效，而且通常要等循环依赖或测试变慢后才被发现。

`ProjectGraphTests` 把项目集合、Target Framework、输出类型、普通 ProjectReference 和 Analyzer Reference 冻结为可执行契约，并显式验证：

- `Protocol -> Core` 是非法边；
- `Teams -> Core/Automations` 是非法边；
- `Automations -> Core/Teams` 是非法边；
- 只有 App 可以启用最终 Runtime Catalog 生成；
- 特定第三方包只能由拥有对应职责的项目引用。

这属于 Fitness Function：架构原则不只靠评审者记忆，而由测试持续检查。

## 新代码应该放在哪里

先按下面顺序判断：

1. 这项语义由哪个业务能力拥有？
2. 它是稳定契约，还是具体实现？
3. 哪些程序集需要消费它？
4. 消费方是否真的需要知道实现类型？
5. 它属于运行时行为、外部协议还是最终装配？
6. 放进去会新增哪条 ProjectReference？
7. 这条边会不会让外围机制反向进入核心？
8. 能否通过已有 Port 协作，而不是再建一层抽象？

几个判断样例：

| 变化 | 推荐位置 | 原因 |
| --- | --- | --- |
| 新增稳定的 Session 命令与结果 | `Abstractions` | Protocol 和 Core 都要围绕同一语义协作 |
| 新增 Session 状态转换实现 | `Core` | 属于权威状态机内部行为 |
| 新增 JSON-RPC 参数兼容规则 | `Protocol` | 只属于外部协议适配 |
| 新增 Cron 解析和 Lease 规则 | `Automations` | 由无人值守调度域拥有 |
| 新增 Mission DAG 规则 | `Teams` | 由多 Agent 编排域拥有 |
| 选择具体模块并注册 DI | `App` 或对应 Module | 属于组合而非业务契约 |
| 新增 Catalog 编译诊断 | `Generators` | 属于编译阶段的声明验证 |

## 常见错误

- 每个类都配一个接口，制造没有变化轴的抽象；
- 把 `Abstractions` 变成跨项目都能随手引用的 Common；
- 为了少写 DTO 映射，让 Protocol 直接暴露 Core 内部类型；
- 让 Core 返回 JSON-RPC、CLI 或 Provider SDK 类型；
- 在 App 中继续编写业务状态转换，让组合根膨胀成 God Object；
- 把运行时 Module Dependency 误当成 ProjectReference；
- 为了“纯净架构”增加大量只有一个实现的 Manager、Factory 和 Facade；
- 只画依赖图，不用架构测试冻结真正的项目引用。

## 本课作业参考答案

### 1. 调用方向与编译依赖方向为什么不同

运行时确实是：

```text
OpenCoWorkJsonRpcConnection（Protocol）
→ SessionService（Core 实例）
```

但编译时双方只围绕稳定 Port 协作：

```text
Protocol → Abstractions ← Core
```

Protocol 的构造函数和代码只认识 `ISessionService`，Core 提供实现，App/Module 在 Composition Root 中把实现注册给接口。这样 Protocol 可以调用 Core 实例，却不需要知道 Core 类型、存储和内部状态机。

### 2. 为什么 ISessionService 属于 Abstractions，而 RowMapper 不属于

`ISessionService` 被多个入口和实现方共同使用，表达 Thread、Turn、Item 的稳定应用语义，并且消费方不应知道具体实现，因此适合成为跨程序集契约。`SqliteThreadRowMapper` 即使被两个类调用，仍然只是 SQLite 实现内部的代码复用，变化原因属于持久化机制；调用者数量不会自动把实现细节升级成公共抽象，它应留在 Core 内部。

### 3. Generator 为什么不是运行时依赖

`OutputItemType="Analyzer"` 告诉 MSBuild 把该项目输出交给编译器作为 Analyzer/Source Generator 使用；`ReferenceOutputAssembly="false"` 表示不要把生成器程序集当作普通引用传入编译结果和运行时依赖闭包。Generator 在构建期间读取语义模型、报告诊断并生成源码，最终程序运行的是生成后的代码，不需要加载 `OpenCoWork.Generators.dll`。

### 4. Assembly 与 Runtime Module 的区别

Assembly/Project 控制编译期类型可见性、依赖闭包和发布产物；Runtime Module 控制服务注册、启动拓扑、停止顺序和运行健康。例如 `SessionModule` 与多个宿主模块都位于 App 程序集，而 `AutomationsModule` 位于独立 Automations 程序集；它们都通过 `IOpenCoWorkModule` 参与同一运行时拓扑，因此两种边界并不一一对应。

### 5. 邮件通知能力应该放在哪里

- 如果多个程序集需要调用稳定通知能力，把窄的 `INotificationSender` 和请求/结果契约放进 `Abstractions`；如果只有 Automation 内部使用，先留在 Automations，不必提前公共化；
- SMTP Client 是外部机制，放在拥有该适配器的实现项目；只有当依赖、发布或复用边界确实独立时才新建项目；
- “什么事件触发邮件、失败如何重试”属于 Automation 规则，放在 `OpenCoWork.Automations`；
- 具体 SMTP 实现与 Port 的 DI 绑定放在 App Composition Root 或对应 Module 的 `ConfigureServices`。

不要因为出现了四个角色就机械创建四个项目。先用现有边界承载，出现独立依赖闭包或变化原因后再拆。

### 6. 放开 Protocol 到 Core 引用的短期收益和长期代价

短期可以少写 Port、DTO 映射和 DI 绑定，Protocol 直接调用具体 Service、读取内部状态甚至操作 SQLite。长期会让协议与存储/状态机共同变化，其他入口容易绕过不变量，Core 重构破坏 Protocol，测试必须拉起更多实现，替换宿主或进程边界更困难，并增加循环依赖风险。省下的是少量显式边界代码，失去的是独立演进、测试替换和统一业务入口。

### 7. 一个 WPF 设备控制项目的最小依赖图

```text
DeviceControl.Wpf ─────────► DeviceControl.Application
       │                              ▲
       └──────────────► SerialAdapter │
                                      │
SerialAdapter ─────────► IDeviceTransport
Application ───────────► Domain
```

- Domain 保存设备、命令和状态转换规则；
- Application 定义 `IDeviceTransport` Port 并编排用例；
- SerialAdapter 实现串口机制；
- WPF 的 `App.xaml.cs` 作为 Composition Root，选择并注册具体 Adapter；
- 一个只把摄氏温度格式化成显示文本的 `TemperatureFormatter` 可以直接做普通类或纯函数，没有必要再配 `ITemperatureFormatter`。
