# OpenCoWork 架构设计总索引

## 这个索引解决什么问题

功能目录只能告诉你“系统有什么”，不能保证你看见藏在代码里的设计能力。本索引按**可独立解释、验证和迁移的设计机制**计数，覆盖当前代码、冻结规格和测试证据。

基线：`dev@050b85c1c42ca2e3bd2abd5eb0943232895081d7`，2026-08-02。

计入索引的项目必须同时满足：

1. 解决一个独立工程问题或守住一个不变量；
2. 能找到当前代码或冻结规格证据；
3. 有可讨论的取舍或失败边界；
4. 能迁移到 OpenCoWork 之外的项目。

纯业务名词、普通 CRUD、重复包装和单纯语法不单独计数。索引数量不是“架构越多越好”的 KPI，只用于防止学习遗漏。

## 每个设计机制最终怎么学

每个 ID 后续都必须展开成一张设计卡：

```text
问题与场景
→ 不变量和约束
→ 当前方案与调用链
→ 为什么放在这一层
→ 替代方案与取舍
→ 生命周期、并发、失败和恢复
→ 代码与测试证据
→ 最小复刻练习
→ 迁移到另一个业务的练习
```

只会说出模式名称不算掌握；能够从约束重新推出类似设计，才算会复刻。

## 学习顺序

不按索引从头背到尾。推荐顺序：

1. `BND + STR + RUN`：先学边界、依赖和生命周期；
2. `STA + SES`：再学状态权威、一致性和恢复；
3. `AGT + TOL`：理解模型执行与副作用安全；
4. `API + CAP`：理解外部契约和扩展演进；
5. `ORC + OPS`：理解可靠编排与长期运行；
6. `GEN + NET + TST`：回头拆解 .NET 落地和证据方法；
7. 每组最后做一次脱离 OpenCoWork 的迁移设计。
