# 第 1 课：项目全景与业务闭环

## 这一课只解决一个问题

OpenCoWork 到底是什么，它为什么不能只写成“调用大模型，然后返回字符串”？

## 一句话答案

OpenCoWork 是一个 .NET 10 代理协作运行时：它让模型对话、工具副作用、多 Agent、无人值守任务和外部渠道共享同一套可恢复、可审计、受权限约束的执行核心。

所以，“模型能回复”只是最外层现象。真正的产品价值是：

- 进程重启后，任务和对话还能恢复；
- 并发请求不会破坏同一会话的状态；
- 模型调用文件、Shell、网络等工具时不能绕过权限和审批；
- CLI、Wire、ACP、Automations、Teams、Gateway 不各造一套会话逻辑；
- Windows x64 与 Apple Silicon macOS 的发布结果有真机证据。

1.0 明确不做桌面/Web UI，也不承诺兼容 DotCraft 的 `.craft`、程序集或私有实现。

## 先用业务语言理解

OpenCoWork 当前覆盖四类业务闭环：

1. **交互式代理**：用户发消息，模型流式回答，必要时调用受控工具；
2. **多代理协作**：Leader 拆 Mission，成员执行 DAG 任务，通过 Mailbox 和 Artifact 协作；
3. **无人值守执行**：Automation 按手动或 Cron 触发，在严格权限和 Lease 下运行并恢复；
4. **外部渠道接入**：Gateway 接收消息、去重、提交 Session，通过 Outbox 可靠发送结果。

这四种入口看起来不同，但都必须落到同一个 Session Core。否则取消、审批、恢复、事件顺序会各说各话，项目很快就会长成一锅状态机粥。

        Thread ─────── Turn ─────── Item

整套设计可以先记成五个稳定中心：

| 中心 | 负责回答的问题 |
| --- | --- |
| `ModuleRegistry` / `WorkspaceRuntime` | 这个进程由哪些模块组成，如何安全启动和停止？ |
| `ISessionService` | 所有入口如何使用唯一的 Thread、Turn、Item 状态机？ |
| `ThreadJournal` / `SessionProjection` | 已发生的事实如何落盘、重放和查询？ |
| `AgentRuntimeExecutor` | 如何把会话历史、配置、模型和上下文变成一次模型执行？ |
| `ToolInvocationPipeline` | 模型产生副作用前必须通过哪些安全步骤？ |

## 七个生产项目分别干什么

| 项目 | 职责 | 学习时的判断口诀 |
| --- | --- | --- |
| `OpenCoWork.Abstractions` | 稳定跨程序集契约和 DTO | 只定义“双方怎么说话”，不放存储实现 |
| `OpenCoWork.Core` | Workspace、Session、Agent、Tool、状态与核心能力实现 | 真正的运行时心脏 |
| `OpenCoWork.Protocol` | Wire、JSON-RPC、ACP 等协议适配 | 翻译，不复制业务状态机 |
| `OpenCoWork.Automations` | 定义、调度、Lease、无人值守恢复 | 编排 Session，不替代 Session |
| `OpenCoWork.Teams` | Mission、DAG、Mailbox、Artifact、Worktree | 编排多个 Session |
| `OpenCoWork.Generators` | 模块、配置和协议目录的编译期生成 | 消灭易漂移的手写注册表 |
| `OpenCoWork.App` | 命令入口和最终宿主组合 | 负责“装起来”，不吞并各层职责 |

关键依赖方向是：外围项目依赖稳定契约，`Protocol` 不直接依赖 `Core` 实现；`Automations` 与 `Teams` 也不能各自复制 Session 状态。

## 一次正常 Turn 发生了什么

以 Wire 的 `turn/start` 为例：

1. `OpenCoWorkJsonRpcConnection.StartTurnAsync` 校验协议输入，并调用 `ISessionService.EnqueueInputAsync`；
2. `SessionService` 在同一 Thread 的协调边界内检查 sequence、状态和幂等键；
3. `SessionService.StartTurnAsync` 先提交 `TurnStarted` 事实，再启动后台执行；
4. 提交过程把事实追加到 `ThreadJournal`，更新内存聚合和 SQLite 查询投影，然后发布 `SessionEvent`；
5. `AgentRuntimeExecutor.ExecuteAsync` 根据冻结的调用快照组装本次模型请求；
6. `DeepSeekResponsesClient.StreamAsync` 读取 Responses SSE，Agent Runtime 把文本、Reasoning、Usage 和工具调用转换为 Session Intent；
7. 如有本地工具调用，统一进入 `ToolInvocationPipeline`，依次通过快照、受众、绑定、权限、Schema、策略、Hook、审批、超时、结果归一化和终态审计；
8. 每个可见状态继续按“Journal 事实 → 投影 → 事件”提交；CLI 或 Wire 订阅者消费 delta，直到 Turn 进入 Completed、Failed 或 Cancelled。

这里最重要的顺序是：**先形成可恢复事实，再让外部看见状态。**

## 为什么 Journal 和 SQLite 都要有

对 Session 来说：

- `ThreadJournal` 是 Thread、Turn、Item 和模型可见历史的权威事实源；
- SQLite 保存可重建的查询投影和其他业务状态；
- 投影落后时可以从 Journal 补齐；
- 不能用“数据库里现在这一行是什么”替代“事情按什么顺序发生过”。

这让重启恢复、幂等、故障诊断和事件顺序有共同依据。代价是写入顺序更严格，但这是这个产品不能偷懒的地方。

## 作业参考答案

下面是按当前代码整理的参考答案。重点不是背这些句子，而是能够从状态所有权、并发、恢复和安全边界重新推导出同样的结论。

### 1. `Thread`、`Turn`、`Item` 分别是什么，为什么不能只保留一张 Message 表？

`Thread` 是一段可长期存在的会话聚合，负责维护模型、工作空间、历史模式、当前序号、活动 Turn、队列和整体可用状态。`Turn` 是 Thread 内由一次输入触发的执行周期，拥有 Running、Waiting、Completed、Failed、Cancelled 等独立生命周期；`Item` 是 Turn 内可以单独记录和推进的最小可观察单元，例如用户输入、模型文本、Reasoning、工具调用或工具结果。

一张 Message 表只能较自然地表达“谁说了什么”，表达不了活动 Turn、排队、审批等待、工具调用与结果关联、非文本内容、局部失败和严格事件顺序。把三层压成 Message，最后仍然要用大量类型字段、状态字段和隐式约定把 Thread、Turn、Item 重新发明一遍，只是边界更模糊。

核对锚点：

- `src/OpenCoWork.Abstractions/SessionContracts.cs`
- `src/OpenCoWork.Core/Sessions/SessionDomain.cs`
- `tests/OpenCoWork.Core.Tests/SessionExecutionTests.cs`

### 2. 为什么 `Protocol` 只能调用 `ISessionService`，不能直接改 SQLite？

`Protocol` 是入口适配器，只负责把 Wire、JSON-RPC 或 ACP 请求翻译成稳定的应用契约；`ISessionService` 才是 Session 状态机的唯一写入口。它集中执行输入校验、expected sequence、幂等键、同一 Thread 的并发协调、状态转换、Journal 提交、投影更新和事件发布。

如果 Protocol 直接修改 SQLite，它会绕过这些不变量，制造“数据库行已经变了，但 Journal、内存聚合、订阅事件和恢复状态都不知道”的分裂状态。更麻烦的是，其他入口也会开始各写一套规则，最终 CLI、Gateway、Automation 对同一个 Session 得出不同结果。

核对锚点：

- `src/OpenCoWork.Protocol/OpenCoWorkJsonRpcConnection.cs`
- `src/OpenCoWork.Abstractions/SessionContracts.cs`
- `src/OpenCoWork.Core/Sessions/SessionService.cs`
- `tests/OpenCoWork.Protocol.Tests/OpenCoWorkJsonRpcTests.cs`

### 3. 为什么 Session 的 SQLite 投影不是权威事实源？

SQLite 投影保存的是从 Session 事实计算出的当前查询结果，目标是让列表、搜索和统计读取更方便；它允许暂时落后、进入 Degraded，也能够根据 ThreadJournal 重建。ThreadJournal 保存按 sequence 排列的已发生事实，历史读取、订阅补发和恢复判断都要回到 Journal。

如果把投影当成权威，只能看见“现在是什么”，看不见“按什么顺序变成这样”，也无法可靠判断某次提交究竟完成到哪一步。把 Journal 作为事实源、投影作为可重建视图，才能同时守住重启恢复、事件顺序、幂等和故障诊断。

核对锚点：

- `src/OpenCoWork.Core/Sessions/ThreadJournal.cs`
- `src/OpenCoWork.Core/Sessions/SessionProjection.cs`
- `src/OpenCoWork.Core/Sessions/SessionRecovery.cs`
- `tests/OpenCoWork.Core.Tests/SessionProjectionTests.cs`

### 4. 为什么工具管线的权限、审批、执行和审计顺序不能随便换？

工具可能修改文件、启动进程或访问网络，所以必须先确认冻结快照中的工具身份和暴露范围，再检查 Binding、Trust、Authority、输入 Schema、策略和 Hook，随后才能请求审批；只有这些条件全部通过，才允许在超时和取消边界内执行。执行后还要先归一化、截断并脱敏结果，再提交稳定终态和审计信息。

顺序交换会直接破坏安全或恢复语义：先执行再审批，副作用已经发生；使用当前 Binding 代替冻结快照，会产生检查对象与执行对象不一致；先发布原始结果再脱敏，会泄漏 Secret；先产生外部副作用却没有记录 attempt，崩溃恢复时就无法判断应该重试还是标记 `OutcomeUnknown`。这条管线本质上是在同时防越权、TOCTOU、敏感信息泄漏和不安全重放。

核对锚点：

- `src/OpenCoWork.Core/Tools/ToolInvocationPipeline.cs`
- `src/OpenCoWork.Abstractions/ToolContracts.cs`
- `tests/OpenCoWork.Core.Tests/ToolInvocationPipelineTests.cs`

## 作业答案的共同结论

四道题虽然分别讨论领域对象、抽象层、持久化和工具安全，背后守的是同一个原则：

```text
所有入口服从同一业务状态机
→ 事实先于投影和对外可见状态
→ 副作用必须经过权限与审批边界
→ 失败后能够根据稳定事实恢复或明确停在未知状态
```

这比记住“用了分层架构、事件溯源、管道模式”更重要。模式名称只是总结，真正可复刻的是这些不变量和执行顺序。
